# Спецификация пилота BibiBike Leads

Версия: 0.2 · этап 2A · 2026-08-09

## Цель

Находить в выбранных публичных Telegram-сообществах сообщения людей, которые
сами выражают намерение открыть бизнес, подобрать франшизу или вложить капитал.
Сохранять только кандидатов, давать менеджеру прямую ссылку и объяснение
срабатывания. Контакт с автором выполняет человек вручную.

Город не является критерием выбора источника на первом пилоте. Если автор сам
назвал город, он сохраняется как дополнительный признак, но поиск источников и
решение о качестве лида от него не зависят.

## Границы

В пилот входят:

- 8–10 вручную выбранных федеральных, предпринимательских и инвестиционных
  публичных групп;
- новые сообщения и редактирование уже замеченных сообщений;
- allowlist, дедупликация, rules-based фильтр и CRM;
- статусы, заметки, аудит и последующая связь со скорингом города.

В пилот не входят:

- автоматический поиск и вступление в группы;
- выгрузка истории чатов без ограничения;
- сбор списков участников, телефонов, Telegram ID и карточек авторов;
- личные сообщения, ответы, реакции и публикации от user-сессии;
- автоматическая продажа или автоворонка;
- обучение модели на Telegram-сообщениях.

## Архитектура

```text
Telethon Reader                     Core service
----------------                    ------------------------------
allowlist only       HMAC POST       aiohttp internal API
read-only events  ────────────────>  intent rules + deduplication
local cursor/outbox                  SQLite owner
heartbeat                            CRM + Aiogram notifications
```

Reader и Core — отдельные процессы одного проекта. Reader физически не должен
иметь функции отправки сообщений или вступления в группы. Он не открывает
основную SQLite. При недоступности Core события остаются в локальной очереди
Reader, а cursor двигается только после подтверждённой доставки.

## Поток данных

1. Администратор регистрирует проверенный публичный источник выключенным.
2. Отдельный аккаунт вручную вступает в группу, resolver сверяет username и ID.
3. После smoke-test администратор отдельно включает источник.
4. Reader периодически получает allowlist через внутренний API.
5. Reader принимает только события из allowlist и выполняет дешёвый локальный
   prefilter, чтобы не отправлять весь чат.
6. Core проверяет HMAC, timestamp, event ID, chat ID и состояние источника.
7. Core строит каноническую ссылку `https://t.me/<handle>/<message_id>`.
8. Rules engine вычисляет score, причины и город.
9. Сообщение выше порога становится лидом; пограничное — кандидатом на ручную
   проверку; нерелевантный текст удаляется по короткому retention.
10. Менеджер меняет статус только в CRM. Ответ выполняется вручную в Telegram.

## Состояния лида

```text
new -> reviewing -> contacted -> qualified -> won
                       |             |
                       +-----------> lost
                       +-----------> disqualified
```

Дополнительно возможен `archived`. Для `lost` и `disqualified` обязательна
причина. Автоматическая переклассификация редактированного сообщения не
перезаписывает решение менеджера: она выставляет `needs_review` и создаёт событие.

## Данные

Core хранит:

- allowlist источников и checkpoint их состояния;
- текст отобранного публичного сообщения, ссылку и время;
- score, сработавшие правила и версию набора правил;
- определённый город и уверенность;
- статус, ответственного и неизменяемую историю действий;
- версионированные snapshots будущего расчёта города.

Core намеренно не хранит профиль автора, список участников, телефон или
Telegram user ID автора. Telegram ID допустим только для внутренних менеджеров.

## Надёжность

- уникальность сообщения: `(source_id, telegram_message_id)`;
- уникальность доставки: `request_id`/`event_id`;
- одинаковое содержимое не создаёт новую ревизию;
- изменение текста увеличивает `revision` и запускает переклассификацию;
- WAL, `foreign_keys=ON`, `busy_timeout` на каждом соединении;
- session Reader хранится отдельно от Core DB и её бэкапов;
- FloodWait выдерживается полностью; ошибка не вызывает ускоренных повторов;
- потеря доступа к источнику переводит его в degraded, без auto-join.

## Этапы

1. **Фундамент:** схема, allowlist, intent rules, ingestion domain, тесты.
2. **Telegram-сессия:** одноразовая локальная авторизация и проверка read-only.
3. **Reader:** live events, edits, cursor, outbox, heartbeat и HMAC delivery.
4. **Core API и бот:** aiohttp, Aiogram, уведомления менеджерам.
5. **CRM:** список, карточка, фильтры, статусы, причины и аудит.
6. **Пилот источников:** 48–72 часа пассивного измерения качества ленты.
7. **Пилот лидов:** одна неделя, ежедневная ручная разметка менеджером.

## Метрики пилота

- кандидаты и лиды в день;
- precision: доля подтверждённых лидов среди показанных менеджеру;
- доля рекламы, инфобизнеса и продавцов франшиз;
- дубли и ошибки определения города;
- медианное время от сообщения до просмотра менеджером;
- число FloodWait, reconnect и недоставленных событий;
- ни одного DM, auto-join или обращения к списку участников.

Критерий перехода к расширению: не менее 70% показанных лидов признаны
релевантными менеджером, нет потерь/дублей после перезапуска и нет действий от
user-сессии кроме чтения allowlist.
